01 / The project

One connected experience instead of disconnected handoffs.

The firm coordinated coaching programs across participating healthcare systems and municipal organizations. As programs expanded, guiding employees to suitable coaches, coordinating Calendly bookings and cancellations, and keeping program engagement reporting current became increasingly complex.

↗

The employee experience

Employees needed an intuitive way to share their development goals, identify relevant coaches, and book or adjust appointments through Calendly without fragmented forms and email exchanges.

≡

The operational challenge

Administrators needed a reliable record of which employees booked, cancelled or rescheduled coaching appointments—linked to the correct coach, program and organization for engagement reporting.

I connected the employee experience, AI-guided coach discovery and scheduling activity into one portal. Calendly remained the scheduling source of truth; the Retool database reflected those events for operational visibility.
02 / Architecture

Retool for the portal. Make for Calendly synchronization.

Retool Apps provided onboarding, conversational AI, coach discovery and reporting. Calendly handled employee appointment changes. Make consumed Calendly events, resolved internal mappings, and synchronized booking records to Retool Database through the PostgreSQL connector. The SQL reports distinguish gross activity from net active reservations.

PART 01 / CONFIGURE THE COACHING ASSISTANT

How the AI was configured for the coaching portal

The base language model already understood natural language. The application supplied the coaching-specific interpretation rules and approved profile vocabulary. Retool stored coach attributes in its database and filtered coach eligibility. The AI did not acquire new model weights, learn coach credentials, or determine scheduling availability.

01
Define its narrow role

Ask guided questions about the employee's goals, strengths, challenges, working context and preferred coaching style. Keep booking actions outside the chat.

02
Curate profile attributes

Maintain coach focus_areas, background_sectors, coaching_styles, interests and a reviewed bio. Active program assignment is checked before showing any coach.

03
Specify one vocabulary

Use distinct categories for goal, development focus, style, sector and interests. For example, career development belongs to primary_goal, not a redundant interest tag with the same meaning.

04
Ask targeted follow-ups

“Difficult conversations” may imply communication, but conflict resolution and confidence require additional evidence. Ask about competing goals instead of silently selecting one.

05
Validate and confirm

JSON schemas and tag allowlists reject malformed values; they do not prove that a valid tag is semantically correct. Show the proposed summary and let the employee correct it before saving.

06
Define evaluation cases

Compare expected responses across direct, ambiguous and multi-skill answers. Review each response for missing tags, unsupported inferences and unclear goals.

Step 3 — Coach matching JavaScript

The ranking function receives employee-confirmed preferences and program-eligible coach rows, normalizes tag arrays, and returns explainable scores. Null or incomplete coach attributes contribute no points rather than breaking the matching query.

retool / rank_eligible_coaches.js
// Retool JavaScript query: rank coaches returned by an authorized
// program-enrollment/coach-eligibility SQL query.
// AI output is reviewed and confirmed before calling this function.
function rankEligibleCoaches(confirmed, eligibleCoaches) {
  const tag = value => typeof value === 'string'
    ? value.trim().toLowerCase() : '';
  const tags = value => Array.isArray(value)
    ? [...new Set(value.map(tag).filter(Boolean))] : [];

  const goal = tag(confirmed?.primary_goal);
  if (!goal || !Array.isArray(eligibleCoaches)) return [];

  const focus = new Set(tags(confirmed.development_focus));
  const interests = new Set(tags(confirmed.interests));
  const style = tag(confirmed.preferred_style);
  const sector = tag(confirmed.work_context);

  return eligibleCoaches
    .filter(coach => coach && typeof coach.id === 'string' &&
      coach.id.trim().length > 0)
    .map(coach => {
      const areas = tags(coach.focus_areas);
      const styles = tags(coach.coaching_styles);
      const sectors = tags(coach.background_sectors);
      const coachInterests = tags(coach.interests);
      const matchedFocus = areas.filter(value => focus.has(value));
      const parts = {
        primary_goal: areas.includes(goal) ? 4 : 0,
        development_focus: matchedFocus.length ? 2 : 0,
        coaching_style: style && styles.includes(style) ? 2 : 0,
        work_context: sector && sectors.includes(sector) ? 1 : 0,
        shared_interest: coachInterests.some(value => interests.has(value))
          ? 1 : 0
      };
      return {
        coach_id: coach.id,
        display_name: coach.display_name || 'Coach profile',
        score: Object.values(parts).reduce((sum, value) => sum + value, 0),
        parts,
        matched_focus: matchedFocus
      };
    })
    .sort((a, b) => b.score - a.score ||
      a.coach_id.localeCompare(b.coach_id));
}
// Optional missing coach arrays contribute zero points, not an error.
// Missing employee goal or unavailable coach results return no ranking.
// Maximum score remains 10; multiple skill overlaps contribute up to 2.

Retool Database · PostgreSQL · Engagement reporting

Booking demand, cancellations and net active reservations

My reporting contribution distinguishes booking events from active appointments: gross bookings capture demand, cancellations capture changes, and net active bookings and reserved hours exclude cancellations as of the report period end. Bookings are grouped by creation date, cancellations by cancellation date, and all active-booking metrics use the period-end snapshot. Reserved hours do not imply attendance or delivered coaching hours.

Program-level metrics, with Retool query bindings

The Retool SQL queries use prepared {{ }} bindings. current_user.sid identifies the signed-in Retool user, while reporting_access.retool_user_id stores the corresponding SID. The selected organization is treated only as a filter: it must match an authorized access row. Retool query-variable spoofing prevention and database resource permissions provide additional enforcement.

sql / program_engagement.sql
-- RETOOL SQL QUERY / program_engagement
-- {{ current_user.sid }} is the signed-in Retool user's stable ID.
-- reporting_access.retool_user_id stores that SID (not email or group ID).
-- {{ organizationPicker.value }} is ONLY a requested filter, not authority.
-- Keep prepared statements and Retool query-spoofing prevention enabled.
-- Maintain database/resource access controls; the picker is not authority.
-- {{ periodStart.value }} and {{ periodEnd.value }} are ISO timestamps.
-- Historical snapshot: active enrollment and active appointments at period end.
WITH scoped_org AS (
  SELECT DISTINCT ra.organization_id
  FROM reporting_access ra
  WHERE ra.retool_user_id = {{ current_user.sid }}::text
    AND ra.organization_id = {{ organizationPicker.value }}::uuid
    AND ra.can_report = true
    AND {{ periodStart.value }}::timestamptz < {{ periodEnd.value }}::timestamptz
    AND isfinite({{ periodStart.value }}::timestamptz)
    AND isfinite({{ periodEnd.value }}::timestamptz)
),
active_enrollments AS (
  SELECT pe.program_id, pe.employee_id
  FROM program_enrollments pe
  JOIN scoped_org s ON s.organization_id = pe.organization_id
  WHERE pe.enrolled_at < {{ periodEnd.value }}::timestamptz
    AND (pe.unenrolled_at IS NULL
      OR pe.unenrolled_at >= {{ periodEnd.value }}::timestamptz)
),
cohort AS (
  SELECT b.*,
      (b.cancelled_at IS NULL
        OR b.cancelled_at >= {{ periodEnd.value }}::timestamptz)
        AS active_at_period_end
  FROM coaching_bookings b
  JOIN scoped_org s ON s.organization_id = b.organization_id
  WHERE b.booked_at >= {{ periodStart.value }}::timestamptz
    AND b.booked_at <  {{ periodEnd.value }}::timestamptz
),
booking_metrics AS (
  SELECT b.program_id,
    COUNT(*) AS gross_bookings_created,
    COUNT(*) FILTER (WHERE b.rescheduled_from_uri IS NOT NULL)
      AS replacement_bookings,
    COUNT(*) FILTER (WHERE b.active_at_period_end)
      AS net_active_bookings,
    ROUND(COALESCE(SUM(EXTRACT(EPOCH FROM (b.ends_at-b.starts_at)))
      FILTER (WHERE b.active_at_period_end),0)::numeric / 3600, 2)
      AS net_active_hours_reserved,
    COUNT(DISTINCT b.employee_id) FILTER (
      WHERE b.active_at_period_end AND ae.employee_id IS NOT NULL)
      AS active_enrolled_employees_with_booking
  FROM cohort b
  LEFT JOIN active_enrollments ae
    ON ae.program_id=b.program_id AND ae.employee_id=b.employee_id
  GROUP BY b.program_id
),
cancel_metrics AS (
  SELECT b.program_id,
    COUNT(*) AS cancellations_in_period,
    COUNT(*) FILTER (WHERE b.was_rescheduled)
      AS reschedule_cancellations_in_period
  FROM coaching_bookings b
  JOIN scoped_org s ON s.organization_id = b.organization_id
  WHERE b.cancelled_at >= {{ periodStart.value }}::timestamptz
    AND b.cancelled_at <  {{ periodEnd.value }}::timestamptz
  GROUP BY b.program_id
),
enrollment_metrics AS (
  SELECT program_id, COUNT(*) AS active_enrolled_at_period_end
  FROM active_enrollments GROUP BY program_id
)
SELECT p.id AS program_id, p.name AS program_name,
 COALESCE(e.active_enrolled_at_period_end,0) AS active_enrolled_at_period_end,
 COALESCE(b.gross_bookings_created,0) AS gross_bookings_created,
 COALESCE(b.replacement_bookings,0) AS replacement_bookings,
 COALESCE(c.cancellations_in_period,0) AS cancellations_in_period,
 COALESCE(c.reschedule_cancellations_in_period,0)
   AS reschedule_cancellations_in_period,
 COALESCE(b.net_active_bookings,0) AS net_active_bookings,
 COALESCE(b.net_active_hours_reserved,0) AS net_active_hours_reserved,
 COALESCE(b.active_enrolled_employees_with_booking,0)
   AS active_enrolled_employees_with_booking,
 COALESCE(ROUND(100.0*b.active_enrolled_employees_with_booking
    / NULLIF(e.active_enrolled_at_period_end,0),1),0)
   AS active_employee_booking_rate_pct
FROM programs p
JOIN scoped_org s ON s.organization_id=p.organization_id
LEFT JOIN booking_metrics b ON b.program_id=p.id
LEFT JOIN cancel_metrics c ON c.program_id=p.id
LEFT JOIN enrollment_metrics e ON e.program_id=p.id
ORDER BY p.name,p.id;

Per-coach engagement breakdown

The second query joins each recorded booking to its resolved coach_id, so a program manager can see activity by coach. Program totals must be computed separately from distinct employee counts; summing unique employees across coaches would overcount an employee who booked two coaches.

sql / coach_engagement.sql
-- RETOOL SQL QUERY / coach_engagement (same dates and definitions)
WITH scoped_org AS (
  SELECT DISTINCT organization_id FROM reporting_access
  WHERE retool_user_id = {{ current_user.sid }}::text
    AND organization_id = {{ organizationPicker.value }}::uuid
    AND can_report = true
    AND {{ periodStart.value }}::timestamptz < {{ periodEnd.value }}::timestamptz
    AND isfinite({{ periodStart.value }}::timestamptz)
    AND isfinite({{ periodEnd.value }}::timestamptz)
)
SELECT p.id AS program_id, p.name AS program_name,
       c.id AS coach_id, c.display_name AS coach_name,
       COUNT(*) FILTER (
         WHERE b.booked_at >= {{ periodStart.value }}::timestamptz
           AND b.booked_at <  {{ periodEnd.value }}::timestamptz)
         AS gross_bookings_created,
       COUNT(*) FILTER (
         WHERE b.booked_at >= {{ periodStart.value }}::timestamptz
           AND b.booked_at <  {{ periodEnd.value }}::timestamptz
           AND (b.cancelled_at IS NULL OR
             b.cancelled_at >= {{ periodEnd.value }}::timestamptz))
         AS net_active_bookings,
       ROUND(COALESCE(SUM(EXTRACT(EPOCH FROM (b.ends_at-b.starts_at)))
         FILTER (WHERE b.booked_at >= {{ periodStart.value }}::timestamptz
             AND b.booked_at < {{ periodEnd.value }}::timestamptz
             AND (b.cancelled_at IS NULL OR
                  b.cancelled_at >= {{ periodEnd.value }}::timestamptz)),0)
             ::numeric/3600,2) AS net_active_hours_reserved,
       COUNT(*) FILTER (
         WHERE b.cancelled_at >= {{ periodStart.value }}::timestamptz
           AND b.cancelled_at <  {{ periodEnd.value }}::timestamptz)
         AS cancellations_in_period
FROM coaching_bookings b
JOIN scoped_org s ON s.organization_id=b.organization_id
JOIN programs p ON p.id=b.program_id AND p.organization_id=b.organization_id
JOIN coaches c ON c.id=b.coach_id
GROUP BY p.id,p.name,c.id,c.display_name
HAVING COUNT(*) FILTER (
  WHERE (b.booked_at >= {{ periodStart.value }}::timestamptz
     AND b.booked_at < {{ periodEnd.value }}::timestamptz)
     OR (b.cancelled_at >= {{ periodStart.value }}::timestamptz
     AND b.cancelled_at < {{ periodEnd.value }}::timestamptz)) > 0
ORDER BY p.name, net_active_bookings DESC,c.display_name;

Booking integrity controls

The database enforces one record per Calendly invitee, consistent booking status and cancellation fields, valid appointment times, and matching organization / program / employee / coach relationships. Uniqueness on reporting access ensures one scope row per user and organization. The ingestion function checks active mappings before committing.

sql / booking_integrity.sql
-- PostgreSQL / schema integrity controls for booking ingestion
-- Tables and their UUID keys follow the Make / Calendly data contract.
-- Validate existing rows before applying these constraints.
CREATE UNIQUE INDEX IF NOT EXISTS ux_booking_invitee
  ON coaching_bookings (calendly_invitee_uri);
CREATE UNIQUE INDEX IF NOT EXISTS ux_reporting_scope
  ON reporting_access (retool_user_id, organization_id);
CREATE UNIQUE INDEX IF NOT EXISTS ux_program_org
  ON programs (id, organization_id);
CREATE UNIQUE INDEX IF NOT EXISTS ux_enrollment_scope
  ON program_enrollments (organization_id, program_id, employee_id);
CREATE UNIQUE INDEX IF NOT EXISTS ux_program_coach
  ON program_coaches (program_id, coach_id);

ALTER TABLE coaching_bookings
  ALTER COLUMN calendly_invitee_uri SET NOT NULL,
  ALTER COLUMN organization_id SET NOT NULL,
  ALTER COLUMN program_id SET NOT NULL,
  ALTER COLUMN employee_id SET NOT NULL,
  ALTER COLUMN coach_id SET NOT NULL,
  ALTER COLUMN booked_at SET NOT NULL,
  ALTER COLUMN starts_at SET NOT NULL,
  ALTER COLUMN ends_at SET NOT NULL,
  ALTER COLUMN status SET NOT NULL,
  ADD CONSTRAINT booking_status_cancel_check CHECK (
    (status = 'scheduled' AND cancelled_at IS NULL)
    OR (status = 'cancelled' AND cancelled_at IS NOT NULL)
  ),
  ADD CONSTRAINT booking_time_check CHECK (
    isfinite(booked_at) AND isfinite(starts_at)
    AND isfinite(ends_at) AND ends_at > starts_at
    AND (cancelled_at IS NULL OR
      (isfinite(cancelled_at) AND cancelled_at >= booked_at))
  ),
  ADD CONSTRAINT booking_invitee_not_blank CHECK (
    length(btrim(calendly_invitee_uri)) > 0
  ),
  ADD CONSTRAINT booking_no_self_reschedule CHECK (
    rescheduled_from_uri IS DISTINCT FROM calendly_invitee_uri
    AND rescheduled_to_uri IS DISTINCT FROM calendly_invitee_uri
  ),
  ADD CONSTRAINT booking_program_scope_fk
    FOREIGN KEY (program_id, organization_id)
    REFERENCES programs(id, organization_id),
  ADD CONSTRAINT booking_employee_scope_fk
    FOREIGN KEY (organization_id, program_id, employee_id)
    REFERENCES program_enrollments(organization_id, program_id, employee_id),
  ADD CONSTRAINT booking_coach_scope_fk
    FOREIGN KEY (program_id, coach_id)
    REFERENCES program_coaches(program_id, coach_id);

Reporting metric definitions

MetricPrecise interpretation
Gross bookings createdCount invitee URIs with booked_at in the period, including replacements and bookings subsequently cancelled
Cancellations in periodCount cancellation events using cancelled_at, regardless of when the original booking was made
Replacement bookingsNew invitee records with a verified rescheduled_from_uri, counted in their new booking period
Net active bookingsBookings created in period and not cancelled before period end; cancellations after period end do not rewrite this historic snapshot
Net active hours reservedTotal scheduled duration of those net active bookings; not completed coaching time
Active enrolled at period endenrolled_at < end and (unenrolled_at IS NULL or unenrolled_at >= end)
Active employee booking rateDistinct employees still enrolled at period end with a net active booking created in the period ÷ active enrolled employees at period end
Coach breakdownSame booking cohort and cancellation definitions, grouped by the coach_id that Make reconciled and stored
Booking reconciliation: An employee books one 60-minute session on Monday and cancels it on Tuesday, then books a replacement 60-minute session on Wednesday. For a reporting period covering those days: gross bookings = 2, cancellations = 1, net active bookings = 1, net active hours reserved = 1.00. The first hour is not included in net active reserved hours. If this was a Calendly reschedule, the new booking additionally has a rescheduled_from_uri link.
Make.com · Calendly · Retool Database

Calendly events become verified booking records with direct database synchronization

Calendly supplies scheduling events, Make handles event capture, identity mapping and reconciliation, and the Make PostgreSQL connector writes normalized booking records to Retool Database. Retool Apps reads those records for program and coach-level engagement dashboards.

The integration path

Calendly (booking / cancellation / reschedule) → Make Watch Events + reconciliation → Make PostgreSQL module → Retool Database tables → Retool Apps SQL reporting

Make uses Retool Database external PostgreSQL connection details to call a parameterized ingestion function. Each event is reconciled against maintained program, coach and employee mappings before it becomes a reportable booking.

05  Make PostgreSQL / Execute a function
    Send typed fields to a parameterized booking ingestion function.
    Transaction: save inbox row -> resolve mappings -> upsert booking.
    Multi-host, unmapped program or unmatched employee -> PENDING_MAPPING.
    Atomic UNIQUE keys handle racing duplicate deliveries.
06  Router / Processing outcome
    APPLIED -> updated Retool Database record feeds SQL reports.
    PENDING_MAPPING -> alert operations for host/program/email resolution.
    PENDING_BOOKING -> retain missing original booking for reconciliation.
07  Make / Error-handler route
    Timeout / rate limit -> retry with 15 min, 1 hr, 6 hr backoff.
    Database unavailable -> queue raw event and attempt count in Data Store.
    Replay to booking_events_inbox after connectivity returns.
08  Scheduled Make / Reconciliation (daily)
    Reprocess pending inbox rows; use Calendly GET event and GET invitee
    to recover missing original booking records and reschedule links.
09  Make / Escalation and backfill
    At 10 processing attempts OR 7 days after received_at, attempt
    Calendly API backfill. If unresolved, mark ERROR and alert operations.
    Keep source event JSON and original invitee URI for investigation.

04 / Engineering judgment

Three design decisions that shaped the build.

The key decisions were dividing responsibilities across the right systems, grounding AI recommendations in coach data, and making scheduling changes reportable without duplicates.

DECISION 01

Keep the employee experience in Retool.

Retool provided the onboarding, AI chat, coach discovery and reporting interface. The chatbot helped employees interpret goals and explore coaches without changing bookings directly.

DECISION 02

Use Make for Calendly event synchronization.

Calendly owned appointments. Make received the create and cancel events, formatted them and wrote verified booking records to Retool Database via PostgreSQL. This dedicated path handled reschedules and failed-delivery retries.

DECISION 03

Treat scheduling activity as structured engagement data.

One Calendly invitee URI mapped to one booking record. Booking, cancellation and reschedule timestamps flowed into a single SQL reporting query, preserving each scheduling action without duplicate records.

05 / Delivery and impact

One coaching journey, with visible scheduling engagement.

The portal connected AI-assisted coach discovery to actual Calendly appointment activity and let program administrators report on bookings, cancellations and reschedules across participating organizations.

Employees could complete onboarding, discuss coaching goals with the chatbot, review relevant coach profiles, and use Calendly to book or change their appointments.

With Make synchronizing Calendly events into Retool, administrators could see which programs generated bookings, how many appointments were cancelled or rescheduled, and how many unique employees booked coaching.

The engagement-reporting SQL used booking records and period-specific timestamps rather than relying on chatbot interactions or assumed session completion. That created a consistent link between scheduling operations and reporting.
